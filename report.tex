\chapter{System Design}\label{ch:design}
% PHASE 1 · target 5.5 pp

The pipeline takes a natural-language circuit description and returns a Verilog testbench,
a Python checker, and a record of everything that happened on the way. This chapter
describes how it is put together and why it is put together that way. The static analysis
layer is the subject of Chapter~\ref{ch:localiser} and is treated here only as one node
among several.

\section{Why a Graph Rather than a Script}\label{sec:design-graph}

Multi-stage LLM pipelines are usually written as imperative scripts: call the model, parse
the reply, call it again, retry on failure. That works until the control flow acquires a
loop. Once a repair step can send execution back to an earlier stage, the conditions
governing that jump are scattered across the function that happens to contain them, and
answering a question such as ``under which circumstances does this configuration
regenerate the driver?'' means reading the whole script.

We built the pipeline as a LangGraph~\cite{langgraph} state machine instead. Every stage is
a node, every transition is an edge, and every conditional transition is a named routing
function that takes the graph state and returns the name of the next node. The routing
functions are small, pure, and testable in isolation; \texttt{should\_repair} decides
whether static findings warrant a repair, \texttt{should\_repair\_after\_eval} decides the
same for compiler and simulator failures, and \texttt{after\_repair} decides where a
repaired testbench re-enters the graph.

This has a practical consequence for the ablation study in
Chapter~\ref{ch:experiment}. The five feedback strategies differ only in what those three
routing functions return; the nodes themselves are identical across all of them. That the
arms are genuinely distinct is therefore a property that can be checked by evaluating the
routing functions over a matrix of states, rather than a property that has to be trusted.

\section{Pipeline Topology and State}\label{sec:design-topology}

The graph has thirteen nodes. Ten perform generation, analysis or evaluation; one is a
fan-in barrier; two implement the two forms of regeneration described in
Section~\ref{sec:design-repair}. Figure~\ref{fig:topology} shows the topology.

\end{minipage}

\label{fig:topology}
\end{figure}

State is a single typed dictionary of thirty-five fields covering inputs, per-stage
outputs, loop control, evaluation results and telemetry. Two fields use LangGraph reducers
rather than plain assignment. \texttt{llm\_calls} accumulates with \texttt{operator.add} so
that the parallel driver and checker branches can each append a log entry without
overwriting the other's, and \texttt{static\_findings} accumulates for the same reason
across repeated analysis passes. The distinction matters: the analysis node runs once per
repair iteration, and a plain assignment would leave only the last pass visible, which is
precisely the evidence needed to answer RQ2.

A second field deserves mention because it exists to correct a measurement error rather
than to implement a feature. \texttt{task\_id} carries the logical identity of a circuit,
separately from \texttt{module\_name}, which carries the Verilog module name. Every
VerilogEval problem defines its module as \texttt{RefModule}, so aggregating on
\texttt{module\_name} would have collapsed all 156 problems into a single row. The bug was
found before the benchmark sweeps rather than after, which was luck.

\section{Generation Stages}\label{sec:design-generation}

Generation follows AutoBench~\cite{qiu2024autobench} in decomposing the task rather than
asking for a testbench in one call, and departs from it in generating the design under test
as well.

\texttt{classify} labels the circuit combinational or sequential from the description
alone. The label controls one routing decision (whether \texttt{standardise} runs) and one
analysis decision (whether the sequential-only checks apply).

\texttt{gen\_dut} synthesises a design from the description. AutoBench withholds the DUT
from generation on the grounds that a faulty DUT would mislead the model; we generate one
because the realistic flow is description to design to testbench, and because a testbench
written with privileged access to the reference answer is not being tested honestly. The
golden design is supplied at evaluation time only, and the field \texttt{eval\_dut\_source}
records which design each run was scored against.

\texttt{extract\_spec} produces a structured JSON summary of ports, behaviour and timing,
and \texttt{gen\_scenarios} turns that into a list of named test scenarios. The two
generation nodes then run as parallel branches: \texttt{gen\_driver} writes the Verilog
testbench, \texttt{gen\_checker} writes a Python checker for its output.
\texttt{merge\_generation} is a no-op that exists solely as a fan-in barrier, so that the
routing decision after generation sees both branches complete rather than racing them.

Model assignment is by task rather than by stage: classification, scenario listing and
mutant generation use the cheaper model, while specification extraction, code generation
and repair use the stronger one. Section~\ref{sec:res-rq4} reports what this costs.

\section{Deterministic Standardisation}\label{sec:design-standardiser}

A sequential testbench must make the design's outputs observable and must toggle the clock.
AutoBench addresses the first with a code standardisation step and reports it as the
largest single contributor to their sequential compilation rate, which rose from 55.47\% to
97.33\%. Their implementation is partly LLM-driven.

Ours is not. \texttt{fdisplay\_inserter.py} is a Python pass that inserts a
\texttt{\$monitor} covering any design output the testbench never observes, and a clock
generator when a declared clock is present but never toggled. Inserting a monitor statement
is a mechanical edit with a single correct answer, and a language model is the wrong tool
for it: it is slower, it costs tokens, and it can decline to do the job in ways that are
tedious to detect.

Three properties make the pass safe to run unconditionally. It is idempotent, marking its
own output with \verb|// [standardised]| and short-circuiting if that marker is already
present. It is fail-safe, returning the input unchanged if anything goes wrong, on the
principle that a missing monitor is a worse outcome than a corrupted testbench. And it
never edits the design, only the testbench.

\section{The Repair Loop}\label{sec:design-repair}

Three sources can trigger a repair: static findings from the analysis layer, compiler
errors from Eval0, and failing scenarios from Eval1. Each is converted into a structured
error report, rendered into a repair prompt alongside the current testbench, and used to
regenerate the driver. The loop is bounded at three iterations.

Two mechanisms stop it wasting effort. Oscillation detection compares a signature of the
current error set against the previous one and halts when they match, on the reasoning that
a model which has already failed to fix an error given that description will not fix it on
a second identical attempt; the check also fires when the regenerated testbench is
byte-identical to its predecessor. Best-so-far retention addresses a subtler problem. The
repair node regenerates the entire testbench rather than patching it, so a later iteration
can be worse than an earlier one. Before this was added, a configuration that repaired more
could score below one that repaired less, which is not a property an ablation should have.
The pipeline now tracks the highest-scoring evaluated testbench and reports that one, while
routing decisions continue to use the current iteration's result.

The second regeneration node, \texttt{regenerate}, exists for the control arm described in
Section~\ref{sec:exp-control}. It draws one additional sample from \texttt{gen\_driver} and
passes it nothing at all: no error report, no static findings, no simulator output. It is
deliberately uninformed.

\section{Evaluation Harness}\label{sec:design-harness}

The harness runs the pipeline over a set of circuits crossed with a set of ablation modes,
writing one JSON record per run. Three guards protect a long unattended sweep.

A budget guard prints the run count implied by a selection and refuses to start if it
exceeds twenty-four runs without an explicit opt-in. This is deliberately low. The refusal
performs zero runs, so an over-broad selection costs nothing.

Two abort conditions distinguish failures that will clear from failures that will not. A
rate limit naming a daily token quota, and an exhausted account balance, both mean that no
later run in the sweep can succeed either; the harness stops immediately and aggregates
what completed, rather than failing every remaining pair one at a time with its own retries
and backoff. An ordinary transient failure does not abort: the run is recorded with status
\texttt{harness\_error} and the sweep continues. Getting this distinction wrong in either
direction is expensive, and the tests assert both behaviours by counting invocations.

\section{Engineering Practices}\label{sec:design-practices}

Prompts are Jinja templates in \texttt{prompts/}, never inline strings, so that they can be
diffed, reviewed, and frozen at a tagged commit before an evaluation run begins
(Section~\ref{sec:exp-freeze}).

Every model call is logged with its node, model, token counts, latency and sampling
temperature. The cost analysis in Section~\ref{sec:res-rq4} is assembled from these records
rather than estimated.

The test suite comprises 201 tests and spends no API tokens. Live-API tests exist but are
marked and skip automatically unless a key is present in the environment, which keeps the
default suite free to run as often as needed. Several of the defects reported in
Section~\ref{sec:loc-falsepos} were caught only because running the full suite was cheap
enough to do after every change.

\chapter{The Static Localiser}\label{ch:localiser}
% PHASE 1 · target 4.0 pp

\section{Design Principle and Scope}\label{sec:loc-principle}

The localiser reads a generated testbench together with the design it instantiates and
reports structural defects. Its scope is fixed by one rule: it detects only what reading
the code can establish. Whether a testbench expects the correct value from a counter after
reset depends on how that counter behaves, which is information the text does not contain.
Whether a testbench drives an input it declared is visible on the page.

That rule is a limitation by construction, and Chapter~\ref{ch:results} shows it to be a
severe one in practice. It is also what makes the layer cheap: analysis is deterministic,
requires no model call, and completes in milliseconds.

Parsing uses Pyverilog~\cite{takamaeda2015pyverilog} to build an abstract syntax tree for
the testbench and the design together. Where Pyverilog rejects the input,
Verible~\cite{verible} is used as a fallback for a basic syntax verdict.

Table~\ref{tab:checks} lists the checks. The final two columns state whether the same
defect would be caught by compiling the testbench or by running it, which is the question

Two rows carry the argument for the whole layer. An output the testbench never observes
cannot be detected by simulation, because a testbench that does not check an output does
not fail on account of it. It passes. The compiler sees legal Verilog and has nothing to
report. The same reasoning applies to \texttt{missing\_fdisplay}, which is the
sequential-specific form of the same defect.

\texttt{clock\_never\_toggled} covers a gap between two other checks. A testbench
containing \texttt{initial clk = 0;} and nothing further has driven the clock as far as the
undriven-input check is concerned, so that check stays silent. The simulation compiles and
runs, but no clock edge ever occurs, the design never leaves its reset state, and every
scenario reads back the reset value. The failure presents as a logic error, which is an
expensive way to discover a missing clock generator.

\section{Width Mismatch: Silent at Simulation Time}\label{sec:loc-width}

Verilog resolves a width mismatch on a port connection by padding or truncating. It is not
an error and, in Icarus Verilog~\cite{iverilog}, not a failure either. Compiling a
testbench that declares \verb|wire [2:0] out| against a design whose port is four bits
produces:

\begin{lstlisting}[language=,basicstyle=\ttfamily\footnotesize]
tb.v:3: warning: Port 3 (out) of module counter_4bit expects 4 bit(s), given 3.
tb.v:3:        : Padding 1 high bits of the port.
\end{lstlisting}

The compiler exits with status zero. The testbench builds, runs, and silently compares the
wrong values. Catching this by simulation is possible but unreliable, since it depends on
whether the scenarios happen to exercise the truncated bits; Section~\ref{sec:val-results}
measures how often they do. The check itself compares each design port's declared width
against the testbench signal bound to it, reading both ANSI and Verilog-1995 declaration
styles, and produces no finding for widths it cannot resolve, such as those given by a
parameter or an expression. Guessing would be worse than silence here.

\section{A Check that was Removed}\label{sec:loc-removed}

A seventh check, \texttt{sensitivity\_list\_error}, was implemented and later deleted. It
looked for \texttt{always} blocks inside the testbench and reported an error when none of
them used \texttt{posedge} or \texttt{negedge} sensitivity, on the reasoning that a
testbench driving a sequential design ought to synchronise to the clock.

The fault-injection study in Chapter~\ref{ch:validation} scored it at zero: of five
injected faults constructed to be exactly the defect it existed to catch, it detected none,
and it had produced the study's only baseline false positive.

The reason is structural. Generated testbenches drive the design from \texttt{initial}
blocks and synchronise using \texttt{@(posedge clk)} event controls, not from
edge-triggered \texttt{always} blocks. The only \texttt{always} block such a testbench
typically contains is its clock generator, which has no sensitivity list by design. The
check was inspecting a construct that the code it analyses does not use.

We removed it rather than repair it. A check with no measured recall and a history of false
positives is worse than no check, because it consumes the repair budget on nothing. The
gap it leaves is recorded in the test suite so that it is not rediscovered later as a bug:
a testbench that drives a sequential design entirely with bare delays is not reported, and
the simulator catches four in five of those.

\section{False Positives as the Primary Risk}\label{sec:loc-falsepos}

A localiser that misses a defect costs one simulation cycle. A localiser that invents one
costs a model call, a regeneration, and the credibility of every finding it subsequently
reports. Four false-positive defects were found during development, all of the same
character: a check that encoded one particular way of writing a testbench and flagged every
other correct way.

The most consequential was not a false positive but its mirror image, and it suppressed
detection outright. Several checks ask questions of the source text, such as whether a
signal is ever compared or printed. Asked of raw source, comments and string literals can
answer those questions with text that is not code:

\begin{lstlisting}[language=,basicstyle=\ttfamily\footnotesize]
$display("PASS: addition_boundary_overflow");   // the word "overflow" appears here
$fdisplay(f, "clk=%b out=%b", clk, out);        // so does an apparent assignment to clk
\end{lstlisting}

The first line made the \texttt{overflow} output of an ALU appear to be observed when the
testbench had stopped checking it. The second made a clock that was assigned once and never
toggled appear to be toggling. Both are false negatives that hide real defects, and the
same class of error was independently found in the Eval1 verdict, where a scenario named
\texttt{immediate\_mismatch} caused its own run to be scored as a failure.

The fix is a preparation pass that blanks the contents of comments and string literals
while preserving length and line breaks, so that callers matching on the prepared text can
still edit the original at the same offsets. Detection for the unobserved-output class
moved from 47\% to 100\% once it was applied.

We report these defects because they bear on how the results should be read. The figures in
Chapter~\ref{ch:results} were produced by a localiser whose measured behaviour moved by
53 percentage points on one fault class during development. The fault-injection study
exists partly because nothing in the ordinary test suite had revealed any of this.

\section{Parse Robustness on Generated Code}\label{sec:loc-parse}

Pyverilog is documented as a research tool and was not written for machine-generated input.
Across the sweeps reported in Chapter~\ref{ch:results} it parsed 81 of 82 testbenches in the
first, and 153 of 153 in the benchmark sweep. The single failure was a testbench that did
not compile either, so nothing was lost by failing to analyse it.

One earlier parse defect is worth recording. Pyverilog concatenates the files it is given,
and a testbench ending in \texttt{endmodule} without a trailing newline was joined to the
following design's \texttt{module} keyword as a single token. The parse failed on every
testbench, the analysis layer returned an empty report, and an empty report is
indistinguishable from a clean one. The static-analysis arm of the ablation was silently
identical to the baseline for an entire round of experiments before this was found.

\chapter{Validating the Localiser}\label{ch:validation}
% PHASE 2 · target 4.0 pp

\section{Why Pass Rates Cannot Answer RQ2}\label{sec:val-motivation}

RQ2 asks how well static analysis narrows down testbench errors before simulation. The
obvious way to answer it is to run the pipeline with the static layer enabled and disabled
and compare pass rates. That answer would be worthless, for two reasons.

A pass rate is a single bit per run. When a testbench fails, the rate does not say which
defect caused it, and therefore cannot say whether the analyser could have caught that
defect. When a testbench passes, the rate says nothing about whether the analyser would
have caught a defect that was never there. Neither outcome constrains the quantity RQ2 asks
about.

The second reason is variance. Chapter~\ref{ch:results} reports a measured spread of 33
percentage points between configurations that execute identical code, which is larger than
any effect the comparison is trying to detect. A difference in pass rates at this sample
size would not be evidence either way.

So we measured the analyser directly, by giving it faults whose identity we already knew.

\section{Fault Injection Method}\label{sec:val-method}

Take a testbench already known to pass. Break it in one known way. Ask three layers the
same question:

\begin{itemize}[nosep,leftmargin=1.4em]
  \item does the static analyser report a finding?
  \item does \texttt{iverilog} refuse to compile it?
  \item does the simulation fail against the golden design?
\end{itemize}

The three-way comparison is what makes the result interpretable. A fault only the analyser
catches is a fault the existing toolchain cannot find at all, and is the strongest possible
case for the layer. A fault the compiler already catches is one the layer adds nothing to
beyond speed. Reporting the first without the second would be selective.

The corpus is 14 testbenches, one per circuit, taken from recorded runs that passed Eval1.
These are real generated artefacts rather than hand-written examples. That distinction
matters, because a hand-written testbench would carry the author's assumptions about what a
testbench looks like, and those assumptions are exactly what the checks encode. Measuring a
checker against inputs shaped by the same beliefs that produced it would flatter it.
Injecting into all 14 produced 215 faults.

\section{Injectors and Negative Controls}\label{sec:val-injectors}

Eight injectors cover the taxonomy. Six target a check directly: renaming a port in the
instantiation, dropping a port connection, narrowing a declared signal width, redirecting
an input's assignments so the input is never driven, removing an output from the
testbench's comparisons, and deleting the clock generator.

Two are negative controls, and they are the more interesting half. \texttt{break\_edge\_sync}
replaces every \texttt{@(posedge clk)} with a bare delay, and \texttt{swap\_bindings} binds
two same-width inputs to each other's signals. Neither is detectable by any structural
check. The second in particular produces a testbench in which every connection is legal and
correctly typed, and only the meaning is wrong.

Including faults the method provably cannot catch is a deliberate choice. A study
containing only detectable faults reports a detection rate that describes the study design
rather than the method. The controls mark where the boundary actually falls, and
Section~\ref{sec:val-limits} states what fell outside it.

\section{Methodological Safeguards}\label{sec:val-safeguards}

Three properties of the harness were necessary to make the comparison mean anything. Each
was added after the corresponding mistake was made.

\textbf{Mutations must produce legal Verilog.} An injector that emits a syntax error would
score as ``the compiler caught it'' for a defect the injector itself introduced. The
undriven-input injector therefore redirects assignments to a fresh register rather than
deleting statements, because deleting a statement can empty an \texttt{if} branch and
produce exactly that artefact. Injectors that cannot mutate a given testbench cleanly
decline, and the declined cases are excluded from the denominator rather than counted as
misses.

\textbf{The corpus must use golden designs, not generated ones.} A recorded run stores the
design the pipeline generated, which can itself be malformed. An early version of the study
compiled mutated testbenches against a generated design that did not build, and scored that
design's defect as a detection of the injected fault. The corpus now loads the reference
design from the fixture set.

\textbf{Every corpus entry is re-verified before injection.} The unmutated testbench must
compile and its simulation must pass against the golden design. Measuring detection against
a baseline that is already failing attributes the baseline's problems to the injected
fault. Entries that fail this gate are excluded and reported.

Three figures summarise the table. Detection is 93\% overall, and 100\% for every class the
method is designed to cover. Localisation, meaning the analyser named both the correct fault
class and the correct signal, is 201 of 215, also 93\%; an exact signal match was required,
so a report naming \texttt{a} does not count as localising a fault in \texttt{data}. On the
14 unmutated testbenches the analyser produced no findings at all.

The false-positive figure is the one we would defend first. A localiser that misses a defect
costs one simulation cycle; a localiser that invents one costs a model call, a regeneration,
and the credibility of every subsequent finding.

Thirty-three of the 215 faults, 15\%, were caught by neither the compiler nor the simulator.
Static analysis found 30 of those, 91\%.

\section{The Case Only Static Analysis Detects}\label{sec:val-unobserved}

The first row of Table~\ref{tab:injection} carries more weight than the rest. Nineteen
faults were injected by removing an output from the testbench's checks; the analyser caught
all nineteen, the compiler none, the simulator none.

The simulator's score is not a shortcoming of the simulator. A testbench that stops checking
an output does not fail on account of that output. It passes, because it is no longer
looking, and it will keep passing however many times it is run. There is no observation the
simulator could make that would distinguish this testbench from a correct one. The compiler
sees legal Verilog throughout.

This is the clearest form of the argument for pre-simulation analysis, and it is worth
stating plainly before Chapter~\ref{ch:results} reports how rarely the situation arises in
practice.

\section{Boundaries of the Method}\label{sec:val-limits}

Binding a port under a name the design does not have is detected by the analyser and by the
compiler equally, at 100\% each. Sixty-two of the 215 faults fall in this class, so a
substantial part of the headline detection rate describes work the existing toolchain
already does. What the analyser contributes there is speed, not capability.

The two control classes were detected at zero, as designed. Swapping two same-width inputs
leaves a testbench in which every port is bound, every signal is driven, every output is
checked, and every width agrees. The defect is in what the testbench means, not in how it is
built, and no amount of reading will find it. The simulator caught 78\% of those, which is
the correct division of labour.

against real circuits and counting.

The design isolates one variable at a time. Comparing the first two sweeps holds the
circuits fixed and changes the model, which tests whether the results depend on model
capability. Comparing the second and third holds the model fixed and changes the circuits,
which tests whether they depend on our choice of circuits. Both comparisons matter for

to be excluded.

Classification, scenario listing and mutant generation use \texttt{gpt-4o-mini} in all three
sweeps. Sampling temperature is 0.7 throughout, which is the supervisor-agreed setting and
reflects realistic use rather than a controlled deterministic condition.

\section{Circuit Sets and Selection Criteria}\label{sec:exp-circuits}

The project set is twelve circuits in two halves. Six are small and were used during
development: two-bit comparators, a D flip-flop, a four-bit counter. Six were written later
and deliberately made harder, with more ports and mixed signal widths: an eight-bit ALU with
carry and overflow flags, a barrel shifter, a nine-port FIFO, an overlapping sequence
detector, a timed traffic-light controller. The second group exists because four of the six
static checks cannot fire on an eight-line circuit with two unambiguous ports, and measuring
a checker on inputs that cannot trigger it is not a measurement.

The third sweep uses VerilogEval~\cite{liu2023verilogeval}, which is the benchmark AutoBench
evaluated on. Running all 156 problems was outside the project's budget, so twenty were
selected. How they were selected determines whether the result is usable, so the procedure
is stated in full.

Every problem was scored before any run took place, using three properties of its reference
design: the number of ports, the number of distinct signal widths, and whether it contains
edge-triggered logic. The twenty highest-scoring problems were taken. Their scores range
from 26.4 to 41.9 against a median of 18.7 across all 156, port counts run from six to
twelve, and fifteen of the twenty are sequential.

The criterion is structural complexity because structural faults are only possible where
structure is complex. This biases the sample \emph{towards} the conditions in which the
localiser can succeed, and that is the point. A null result obtained under favourable
conditions is stronger than one obtained under arbitrary conditions.

The alternative procedure, running all 156 and reporting the twenty that produced findings,
would have selected on the outcome. It would have produced a better-looking number that
meant nothing, and it would not have survived the first question about how the circuits were
chosen.

\section{Ablation Arms}\label{sec:exp-arms}

Five configurations differ only in which feedback sources are permitted to trigger a repair.

\midrule

Section~\ref{sec:design-graph} behave differently. That the arms are genuinely distinct was
checked by evaluating those functions over a matrix of states rather than assumed.

\section{The No-Diagnostics Control}\label{sec:exp-control}

Every repairing configuration receives something the baseline does not: a second generation.
If \texttt{hybrid} outperforms \texttt{baseline}, two explanations fit equally well. The
feedback may have identified the defect and guided the repair. Or the model may simply have
had a second attempt, and sampling twice from a stochastic generator produces a better
result often enough to explain the gap without any feedback being involved.

\texttt{retry\_only} separates them. It draws exactly one additional sample from
\texttt{gen\_driver} and passes it no error report, no static findings and no simulator
output. Any configuration must beat \texttt{retry\_only}, not merely \texttt{baseline},
before its feedback can be credited with the improvement.

AutoBench's ablation has no equivalent arm. Its reported gains of roughly 8\% from
auto-debug and 10\% from scenario checking are measured against versions of the system with
those mechanisms disabled, which also removes the regeneration attempts they trigger. The
comparison therefore cannot distinguish the two explanations above.
Section~\ref{sec:res-rq3} reports what happens when the control is present.

\section{Prompt Freezing}\label{sec:exp-freeze}

All nine prompt templates were frozen at a tagged commit before the first sweep and were not
modified afterwards. The tag records a checksum of the template set so the claim can be
checked rather than taken on trust.

The protection this offers is against a specific and easy mistake: observing a poor result,
adjusting a prompt, re-running, and reporting the improved number as though the prompt had
been fixed in advance. One caveat has to be stated alongside it. The driver prompt was tuned
during development against the six original project fixtures, so those six are not held out.
The six purpose-built circuits and all twenty VerilogEval problems were never used for
prompt tuning.

\section{Statistical Treatment}\label{sec:exp-stats}

Pass rates are proportions from small samples, and the usual normal approximation behaves
badly at the extremes. Confidence intervals are therefore Wilson score
intervals~\cite{wilson1927}, which remain sensible when a proportion approaches zero or one.

Comparisons between arms use Fisher's exact test~\cite{fisher1922} rather than a chi-square
test. With 44 runs per arm and pass counts in the range of nine to eighteen, several cells
of the contingency tables fall below the expected-frequency threshold at which chi-square is
valid. Fisher's test makes no such assumption.

Both are computed by \texttt{scripts/analyse\_results.py}, which reads the same JSON records
the pipeline writes. No figure in Chapter~\ref{ch:results} was transcribed by hand.

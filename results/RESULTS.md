# Results Index

Every experiment in this project, in one place. Each sweep has its own `REPORT.md` with
per-circuit detail; this page is the entry point.

**Source of truth is the JSON.** Each run writes `results/<sweep>/<run_id>.json` containing the
generated circuit, the final testbench, every AI call with tokens and latency, all static
findings, the mutants, and the full repair history. These Markdown files are a *view* on that
data, generated by `scripts/render_report.py`. They never replace it.

To read a run's Verilog side by side with the golden circuit:

```bash
python scripts/show_run.py --list                  # find a run
python scripts/show_run.py <run_id>                # one run, extracted to files
python scripts/show_run.py --circuit counter_4bit  # every run of one circuit
python scripts/show_run.py --compare               # generated vs golden, all runs
```

Output lands in `results/inspect/` and is not committed — regenerate it rather than keep it.

## Eval0 — compile rate, and how it compares to AutoBench

| Slice | SEQ | CMB | Total |
|---|---|---|---|
| Strong model (`claude-sonnet-4.5`) | **98.7%** (77/78) | 97.6% (41/42) | **98.3%** (118/120) |
| Weak model (`gpt-4o-mini`) | 84.5% (93/110) | 96.0% (48/50) | 88.1% (141/160) |
| **Pooled** | **90.4%** (170/188) | **96.7%** (89/92) | **92.5%** (259/280) |

**Against AutoBench** (Qiu et al., GPT-4-turbo, 156 circuits):

| Sequential Eval0 | Rate |
|---|---|
| AutoBench **without** their standardisation script | **55.5%** |
| AutoBench **with** it — their headline, and their largest single gain | **97.3%** |
| **Ours with the standardiser inert** (the 182 SEQ runs it never touched) | **90.7%** |
| Ours, strong model, all modes | **98.7%** |
| Ours, strong model, `hybrid` | **100%** (22/22) |
| Ours, pooled over both models | 90.4% |

**At comparable model strength we match or slightly exceed them** — 98.7% vs 97.3% sequential,
98.3% vs 95.7% overall — and on harder circuits, since our benchmark subset is the hardest
quintile. **Pooled we do not**: 90.4% sequential is ~7 points behind, entirely because half our
runs used a cheap model they never tested.

**The deterministic standardiser (pipeline node 8) is not what earns this.** It fired on only
**6 of 188** sequential runs. The other 182 are effectively un-standardised and still compile at
**90.7%** — 35 points above AutoBench's un-standardised 55.5%. Even the weak model reaches
84.5% unaided. The defect class their script existed to fix has largely disappeared from
current models; the same technique now has almost nothing to do.

> ⚠️ **Unverified mechanism.** A missing `$fdisplay` causes a *functional* failure, not a
> *compile* failure, so it is not obvious how inserting one lifts Eval0 by 42 points. Either
> their script does more structural normalisation than our summary of the paper records, or the
> gain has another cause. Resolve this from the paper before leaning on "same technique,
> opposite outcome" in the report.

Note `retry_only` has the **worst** sequential compile rate of any mode (81.8%) — consistent
with the separate finding that a blind extra attempt can make the output worse.

## Eval1 by mode and sweep

The primary result. Each cell is "testbenches that passed / testbenches run".

| Mode | `final_hard_r1` | `weak_model_r1` | `verilogeval_weak` | `verilogeval_strong` |
|---|---|---|---|---|
| `baseline` | 8/12 (67%) | 2/12 (17%) | 2/20 (10%) | 5/20 (25%) |
| `retry_only` **(control)** | 8/12 (67%) | 3/12 (25%) | 2/20 (10%) | 6/20 (30%) |
| `compiler_only` | 8/12 (67%) | 6/12 (50%) | 1/20 (5%) | — |
| `pyverilog_only` | 4/12 (33%) | 4/12 (33%) | 1/20 (5%) | — |
| `hybrid` | 10/12 (83%) | 6/12 (50%) | 2/20 (10%) | 10/20 (50%) |

**How to read this.** `retry_only` is the control — it gets one extra generation attempt with
**no diagnostic information at all**. A mode must beat `retry_only`, not merely `baseline`,
before its feedback can be credited with the improvement.

- `hybrid` leads in three of four sweeps.
- `hybrid` vs `retry_only` pooled: **p = 0.372** — not significant.
- On the strong benchmark sweep: 50% vs 30%, **p = 0.219** — not significant at n=20.
- `retry_only` vs `baseline`: **p = 1.000** — the bare extra attempt is worth nothing, so any
  real gain sits on the diagnosis rather than the retry.
- ⚠️ Pooled across matched circuits, hybrid beats the control 11–2, **p = 0.022**. This is
  **post hoc**, fails correction for multiple comparisons, and must be reported as
  *suggestive, not established*.

## What actually triggered each repair

The mechanism behind any gain, across all 280 runs:

| Trigger | Repair iterations |
|---|---|
| simulation (ran, got wrong answers) | **79** |
| blind retry (no information — the control) | 64 |
| compiler errors | 10 |
| **static analysis (Pyverilog) — the project's contribution** | **1** |

**This is the central finding.** The static localiser triggered exactly one repair in the
entire study, and that one (`Prob150`, `verilogeval_strong`) was subsequently undone by the
repair loop. `pyverilog_only` performed **0 repairs across 44 runs**.

The localiser is not broken — a dedicated fault-injection study puts it at **93% detection,
93% localisation, 0 false positives over 215 injected faults**, including 30 of 33 faults that
neither the compiler nor the simulator can see. The structural defects it detects have simply
become rare in output from current models: **87% of our observed failures are semantic**, and
no structural check can catch a wrong expected value.

## Parser coverage

Which parser read the testbench on the final analysis pass of each run:

| Sweep | Pyverilog | Verible fallback |
|---|---|---|
| `final_hard_r1` | 56 | 4 |
| `weak_model_r1` | 41 | 19 |
| `verilogeval_weak` | 40 | 60 |
| `verilogeval_strong` | 40 | 20 |
| **Total (per run)** | **177** | **103** |

Counting *every* analysis pass rather than one per run, the figure is **262 of 434**.

⚠️ **A Verible fallback means none of the six structural checks ran.** Verible gives a
syntax-valid verdict only. The record still says `parse_ok`, which is why `REPORT.md` shows
"Pyverilog parse failures: 0" — that field does not distinguish the two parsers. Use the table
above, not that line.

⚠️ **The unreadable files are not a random sample.** Runs Pyverilog could read pass Eval1 at
**45.6%**; runs that fell back to Verible pass at **6.0%** (Fisher p < 0.0001). The null result
for static analysis is therefore measured on the healthier subset of its own input.

## How far the generated design diverges from the reference

The pipeline writes its own design (node 2) and is marked against the golden one. Comparing
the two interfaces across every run (`python scripts/show_run.py --compare`):

| | |
|---|---|
| Runs whose generated design matches the golden interface | **273 / 280 (97.5%)** |
| Runs that differ | **7** |

**All 7 are the same circuit — `Prob150_review2015_fsmonehot` — and every one invents a clock**
(`clk` plus some of `reset` / `rst` / `rst_n`). It happens under both the weak and the strong
model and in all five modes, so it is driven by that problem's description rather than by
sampling noise. All 7 fail Eval1.

⚠️ **This compares the port interface only.** Two designs with identical ports can still
behave differently, and no equivalence check was run. So this bounds the *structural* side of
the co-generation concern — it does not establish that the other 273 designs are functionally
correct.

## Known limitations recorded in the data

1. **Co-generation.** The localiser reads the *generated* circuit while evaluation compiles
   against the *golden* one, in all 280 runs. Measured, not excluded — see
   `golden_reanalysis.json`, and the interface comparison above which localises the structural
   divergence to a single circuit.
2. **Parse coverage is a selection effect**, not merely a gap — see above.
3. **Eval2 is at a ceiling** and discriminates nothing between modes. The cause is fixture
   size, established by a pre-registered pilot that varied mutant quality and circuit choice
   independently.
4. **Intermediate testbench versions are not stored.** `repair_history` records the trigger and
   error signature per iteration, but only the final retained testbench is saved. A
   before/after code diff across repair iterations cannot be reconstructed from these files.
5. **The 20-circuit VerilogEval subset is the hardest quintile**, not a random sample. The
   selection weighting was never committed and is not recoverable; the subset is defended by
   its recomputable outcome (6–12 ports vs median 4 across the other 136 problems).
